# Importers

Status: normative. Every importer produces proposals that go through the write path at tier T3 (write-path.md §10.4). Importers never write tables directly.

Imports are written as client `cli_import`, not as the app the data came from, so an import never counts against an app's limits and is never undone with it. They skip the hourly save quota and the repo check (rule 2 already keeps repository files out) and make no per-item LLM call; the extractor (§3) is the only model call, paid from the import budget.

## 1. Rules for every importer

1. **Owner-run only.** `mema import --commit` needs one step-up per batch (write-path.md §10.5); `--dry-run` needs only the PC grant, sends counts only to `POST /v1/import/estimate`, and returns the cost estimate, never content.
2. **User-level sources only.** Importers never read files inside a repository (no repo `CLAUDE.md`, `AGENTS.md`, `.cursor/rules`, `.claude/`), because a cloned repo's files are attacker-authored.
3. **Skip own output.** Any file or block containing a memory-anywhere marker (`generated by memory-anywhere`, `memory-anywhere:begin`) is skipped.
4. **Redact first.** Items are redacted (write-path.md §3) on the client computer before upload; the server redacts again.
5. **Idempotent.** Idempotency key = `sha256(source_type ‖ source_item_id ‖ extractor_version ‖ ordinal)`. For list sources without ids, `source_item_id` = `content_norm_hash` of the item, so re-importing the same list is a no-op and an edited item is a new item.
6. **Suppression wins.** A forgotten or purged fact that is still in a vendor's memory is rejected on re-import (`previously_forgotten`, row D8; imports never elicit), so vendor memories cannot resurrect it.
7. **Dry run first.** `--commit` is refused unless a dry run of the same file (same SHA-256) ran in the last 24 hours.
8. Upload: the client posts items to `POST /v1/admin/import` in requests of ≤ 100 items and ≤ 1 MiB, each carrying the approved `batch_id`, with the batch's multi-use step-up token (60 minutes). An interrupted import resumes with `--resume <batch_id>` and a fresh step-up; items already recorded are skipped by their idempotency keys.

Cursor user rules live in the app settings, not a file; the owner pastes them with `paste --vendor cursor`.

"atomic → active T3" means decision rows D1–D10, D12 and D13 apply (write-path.md §10.4), then the item is stored active at T3 if it passes. T3 items are recalled but never enter the profile. An imported preference also creates a `preference_confirm` review item, so the owner can promote it into the profile with one tap. "observation" means the item becomes an observation mention with session key `import:<batch>:<file or conversation id>`; it is promoted only if the same fact recurs in another conversation, another source, or a live save.

Model-written coding-tool memories go to observation because those tools write them after reading web and tool output; importing them as memories would launder injections.

The vendor summaries are the same memories as the vendor's list, written as prose by the vendor, so they need the extractor to split them into facts, but their facts are stored like the list's (active T3), not held for recurrence like a history's. The span check (write-path.md §10.2) still keeps every fact tied to the vendor's own words.

Sensitive items: an item about the owner in a sensitive category (health, money, religion, politics, sex life, immigration, criminal history, home address) is not rejected but held for the owner's review (`import_sensitive`, write-path.md §10.4), because the owner started the import with a passkey and the facts are the owner's own. The review page offers to approve all of one import's held items at once, with one passkey; that stores each at T3 and lets every connected app recall its category. Other people's private details are still rejected.

Dates: an item said at a known time keeps that day as `valid_from` (and as an observation's first sighting), but an imported observation expires counting from the import, not from when it was said, so old history can still recur and be promoted.

## 3. History extraction

- Parsers keep only messages authored by the user. The role field and structure for each export format are verified against a real export and recorded as fixtures in `evals/datasets/i/` (synthetic copies, no owner data committed). If the format differs from expectations, the importer is adjusted.
- Extraction uses the extractor prompt (memory-policy.md §6.12, version `extract_import/2`) over batches of up to 20 user messages from one conversation, with the span check (write-path.md §10.2). The extractor extracts the owner's own sensitive facts too, which are held for review (§2); it never extracts other people's private details.
- Budget: write-path.md §10.5. `import_usd_cap` is $50 across all imports; the estimate is shown first and must be confirmed. At the cap the batch stops as `aborted_budget` and `--resume` continues it.
- Filters: `--since`, `--until`, `--conversation-min-user-turns <n>` (default 2).
- Pasted documents inside user messages: a user message longer than 4,000 chars is split into paragraphs, and paragraphs that look like quoted material (more than 70% of lines start with `>` or the paragraph is fenced code) are dropped before extraction.

## 4. Re-import of native memories

- Native vendor memories can stay on; memory-anywhere is canonical.
- Re-import is manual: `mema import --source <vendor>-memory` with pasted text. The daily digest reminds the owner weekly ("Last ChatGPT memory import: 23 days ago").
- Idempotency (rule 5) makes repeated imports converge: unchanged items are no-ops, edited items are new T3 items (over a `one` slot held at T3 they update it, per the rights matrix in write-path.md §8.2; over a slot held at T0–T2 they become historical if undated, else contested), forgotten items are rejected.
- Codex `/import` and Claude Code `/import` copy memories between tools, so the same fact may arrive from several sources; rule 1 of the store rules (hash match) adds a source instead of a duplicate.

## 5. Import report

`--dry-run` and `--commit` print: items read, skipped (marker, empty, redacted), and by outcome and reason; for history, conversations and user messages read, estimated and actual cost. `import_batch.counts_json` stores the same counts (no content), and `GET /v1/import/batches/<batch_id>` returns them with the batch's status and the items still waiting for the extractor.

## 6. Gates

Suite I (`pnpm eval run --suite I`) runs the real importers and the server's import path on the synthetic exports in `evals/datasets/i/imports/` (labels in `labels.jsonl`), each case on a fresh store, with a scripted extractor (`evals/datasets/i/fake-extractor.json`), so it needs no API key.

- Re-importing the same file leaves the content hash unchanged (data-model.md §12; the store hash changes because each run records an `import_batch`). Every fixture.
- Duplicate rate on a labelled synthetic export pair (the same 20 facts as a Claude list and a ChatGPT list) ≤ 5%, with a Wilson CI: a stored memory is a duplicate when another current memory holds the same labelled fact.
- No false merges on a labelled distinct pair (22 near but different facts from the same two sources: other drinks, cities, years, people, distances): 0 of n, n ≥ 20. The result records each pair's cosine, so the margin to store rule 6's thresholds (write-path.md §12) is visible.
- Extraction precision and recall on the labelled history and summary exports, reported with Wilson CIs. The scripted extractor states every labelled fact plus noise, some of which the span check must drop, so this measures what the write path keeps, not a model's extraction.
- S-POI-09: repo files never read; model-written sources never become active memories without recurrence.
