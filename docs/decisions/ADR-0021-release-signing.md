# 0021 Release signing with minisign; dev key for spike and eval stages

Status: accepted
Date: 2026-11-07

## Context
The instance installs only signed tarballs, but v3 never said who makes the key or how a spike build is signed before the release workflow exists (round-3 audit B5).

## Decision
Two minisign keys. The release key is generated by the owner once before M2; its private half lives in a GitHub Actions environment secret (manual approval) plus an offline copy; `prod` trusts only it. The dev key is generated by Claude Code in M0, stays on the PC, and is trusted only by `spike` and `eval-*` instances. The CI release workflow exists from M2; npm publishing from M5. Spec: deployment-aws.md §7.4.

## Consequences
M0 does not wait for release infrastructure. A dev-signed build cannot run on `prod` without a stack change (which could replace the trusted key files through user data); every such change is alerted (deployment-aws.md §2), and the deploy session that could make it is short and owner-started (ADR-0020). The release key has no password, because CI cannot type one; the GitHub environment's manual approval and the offline copy protect it.
