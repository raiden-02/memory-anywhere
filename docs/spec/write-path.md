# Write path

Status: normative. Every write goes through this pipeline: live saves from any client, spooled saves, prompt capture, imports, observation promotion and owner edits. There is no second path. An LLM may propose an attribute, extract candidates or downgrade a borderline save. It never deletes, hides or supersedes anything.

## 1. Pipeline

| Step | Name | Where | Section |
| --- | --- | --- | --- |
| 0 | Authenticate, authorize, rate-limit, validate schema | server | §2, mcp-interface.md §6 |
| 1 | Idempotency check | server | §2.3 |
| 2 | Redact (prompts, capture, import text) | client for prompts and spool; server again for everything | §3 |
| 3 | Extract candidates (capture and history import only) | server job | §10 |
| 4 | Normalize and verify | server | §4 |
| 5 | Policy decision table → outcome | server | §5 |
| 6 | Resolve entity, attribute, section | server | §6 |
| 7 | Store rules → insert, add source, update, contest | server, one `BEGIN IMMEDIATE` transaction | §8 |
| 8 | Commit with events, FTS, embedding, write_request | server, same transaction | §11 |

Order detail: the deterministic part of step 6 (§6.1 steps 1, 2.1, 2.2, 3–5) runs before step 5, because rows D3, D16 and D17 need it. The LLM slot proposal (attribute step 3) runs only when no row from D1 to D13 has decided, just before D14. Implementations MUST compute resolution once and pass it to the decision table and the store rules.

## 2. Channels, tiers, sessions, idempotency

### 2.1 Channels

| Channel | Entry point | Caller class | Base tier |
| --- | --- | --- | --- |
| `mcp` | `tools/call memory_save` on `/mcp` | from `client_policy.class` (`chat` or `coding`) | T2 |
| `spool_save` | `/v1/writes` entry with `op: save` | `coding` | T2 |
| `capture` | job `extract` over `session_prompt` rows | `capture` | T2 |
| `import` | `mema import` (step-up) | `import` | T3 |
| `admin` | admin UI (passkey session; in local mode a session opened with the local token), or a CLI admin command with a step-up token | `admin` | T0 |
| `promotion` | observation promotion (§8.3) | inherits | lowest counted mention tier |
| `review_approve` | owner approves a review item | `admin` | T0 |

Channels `promotion` and `review_approve` enter directly at the store rules (§8) with the content already screened; they do not re-run the decision table.

A save becomes T1 only when the server ran an elicitation and the user answered Yes in a client whose policy has `elicitation = verified` (§5 rows D5 and D15). Model-supplied fields (`user_words`, `explicit_request`, `why_durable`) never change the tier. ADR-0002.

### 2.2 Session key

Used for observation promotion and dynamic-section candidates.

| Caller | Session key |
| --- | --- |
| Coding tool via proxy | `client_id:MA-Session` (proxy instance id) |
| Coding tool via `/v1/writes` (hooks, spool) | `client_id:<hook session_id>` |
| Chat app | `client_id:<6-hour bucket>` where bucket = floor(epoch seconds / 21,600) |
| Import | `import:<batch_id>:<conversation or file id>` |
| Admin | `admin` |

Two mentions are "from distinct sessions" when their session keys differ, except that two chat keys of the same client also need `observed_at` at least `observation.chat_session_gap_hours` (6) apart. Session keys built from client headers are labels, not security boundaries.

### 2.3 Idempotency keys

| Channel | Key |
| --- | --- |
| `mcp` from the proxy | `pxs_` + ULID generated by the proxy per `tools/call`, sent as `_meta["memory-anywhere/idempotency_key"]` |
| `mcp` from any other client | `sha256(client_id ‖ content_norm_hash ‖ kind ‖ sha256(norm(user_words)) ‖ explicit_request ‖ supersedes ‖ floor(epoch_seconds / 21600))`, fields joined with `"\n"`, absent fields as empty strings. The 6-hour bucket matches the chat session rule (§2.2), and a retry that adds or changes `user_words` or `explicit_request` (for example after a server hint) is a new request |
| `spool_save`, `prompt` | the spool record's `idempotency_key` (`spl_` + ULID) |
| `capture` | `sha256("capture" ‖ session_prompt.id ‖ extractor_version ‖ ordinal)` |
| `import` | `sha256(source_type ‖ source_item_id ‖ extractor_version ‖ ordinal)` |
| `admin` | `adm_` + ULID per request |

If `write_request` already holds the key, the server returns the stored `result_json` unchanged and does nothing else. Results of type `input_required` (an elicitation in progress, §5) are never written to `write_request`; only the final result of the retried call is. A repeat is never a new mention and never a new source. `memory_save` is annotated `idempotentHint: true` on this basis.

## 3. Redaction

- One implementation, `packages/contracts/src/redact.ts`, used by the client (before spooling or sending prompts) and the server (on every inbound text field).
- Patterns: memory-policy.md §3.7. Each match is replaced with `[REDACTED:<type>]`.
- For `memory_save`, a secret match does not redact: it rejects (§5 row D1), and the content is never stored or logged.
- For prompts and capture, redaction replaces and continues. Extracted candidates containing `[REDACTED:` are dropped.
- Logs never contain request bodies (operations.md §1).

## 4. Normalize and verify

1. Strip CR, LF, tab and other control characters (Unicode category Cc and Cf except ZWJ) from `content`, `user_words` and `why_durable`, replacing each run with one space; trim.
2. Truncate checks: `content` 1–400 chars, `why_durable` 1–200, `user_words` ≤ 200, else `INVALID_INPUT`.
3. `content_norm_hash` = sha256(norm(content)).
4. Compute `qualifying_user_words` (memory-policy.md §3.5).
5. Coding-tool `user_words` check: for callers of class `coding` in a repo with prompt logging (every enabled repo), if `user_words` is present it MUST occur, after `norm()` on both sides, as a substring of a `session_prompt` from the same `client_id` and `repo_key` received in the last 24 hours. If it is not found at once, the server re-checks every 250 ms for up to 1.5 s (the async prompt hook may still be in flight). If it is still not found, `user_words` is treated as absent for every rule below, and the result reason gets the suffix `; user_words not found in your prompts`. This catches invented quotes. It does not raise the tier, because a prompt may contain pasted text the user did not write.
6. `remember_intent` = memory-policy.md §3.4 on `user_words` (after step 5).
7. Screens computed once: `secret_hit`, `instruction_hit` (memory-policy.md §3.2), `sensitive_category` (memory-policy.md §7.1; first category whose lexicon matches; the LLM `sensitive_check` may add one after D2, §6.2), `short_lived_hit`, `suppression_hit` (§9.2).

## 5. Policy decision table

Evaluated top to bottom; the first matching row decides. `tier` is the channel's tier (§2.1). "Elicit" means: if the client policy has `elicitation = verified` **and** the request's `clientCapabilities` declares elicitation, return an MCP `InputRequiredResult` (mcp-interface.md §5) whose question quotes the first 200 characters of `content` and names the slot or category; on Yes the save continues at T1 as the row says; on No the outcome is `rejected` reason `user_declined`; otherwise (no capability, not verified, or 5-minute timeout) the row's "else" branch applies.

Pre-checks (errors, not outcomes): grant valid and client not revoked; `client_policy.write = 1`; for class `coding`, `MA-Repo-Key` is an enabled repo (`REPO_NOT_ENABLED`); quotas (`RATE_LIMITED`); schema (`INVALID_INPUT`); idempotency (stored result).

| --- | --- | --- | --- | --- |

| D2 | `instruction_hit` and tier > T0 | review | `instruction_needs_owner` | memory `pending_review`, kind `instruction`; review kind `instruction` |
| D3 | `sensitive_category` and (entity ≠ self or section resolves to People) | rejected | `sensitive_third_party` | nothing |

| D18 | `qualifying_user_words` | active | `user_stated` | §8 |
| D19 | otherwise | observation, or active if promotion triggers | `model_inferred` / `recurred` | observation mention |

Rules for the table:
- A client whose section allow-list is not `["*"]` always has `save_floor = observation` (the admin UI enforces this), so restricted clients cannot write into sections they cannot read.
- Rows D1–D2 run before any LLM call; `sensitive_check` is the only call before D3, and the slot proposal runs only just before D14.
- The optional durability judge (§6.2) runs only when the outcome came from D14–D18 and tier ≥ T2. It may change `active` to `observation` (reason `judge_not_durable`). It never changes any other outcome.
- Rows apply to every channel. For `capture`, `explicit_request` is set when the source prompt shows remember intent, and `user_words` = the extracted span. For `import`, rows D11, D13b and D14–D19 are replaced by §10.4, and D13 applies without the `qualifying_user_words` condition.
- A `review` outcome creates a `pending_review` memory. It is not recalled, projected or profiled. `memory_profile` shows "N items await your review in the admin UI" when N > 0.
- At T0, rows D2, D7 and D8 do not apply and D10a decides (the owner's word is final); D1 (secrets) and D3 (third-party sensitive) still reject, and D4 applies to sensitive content. A T0 save that matches a suppression lifts it.

### 5.1 Outcomes

| Outcome | Meaning | Where the data goes |
| --- | --- | --- |
| `active` | Stored and recalled | `memory` with status `active` or `contested` (store rules decide) |
| `observation` | Staged; never recalled; promoted on recurrence | `observation`, `observation_mention` |
| `review` | Waits for the owner | `memory` with status `pending_review`, `review_item` |
| `rejected` | Not stored | nothing except `write_request` (ids and reason only) |
| `queued` | Client-side only: spooled while offline | spool file |

### 5.2 Reason codes

`already_stored`, `owner`, `update`, `correction`, `contested`, `event`, `explicit`, `stated_preference`, `slot_fact`, `user_stated`, `recurred`, `single_mention`, `model_inferred`, `client_floor`, `judge_not_durable`, `instruction_needs_owner`, `sensitive_confirmed`, `sensitive_needs_owner`, `sensitive_third_party`, `sensitive_not_requested`, `previously_forgotten`, `short_lived`, `secret`, `user_declined`, `capture_no_llm`, `unsupported_span`, `historical`, `imported`, `imported_observation`, `repo_not_enabled`, `offline`. Each code has a fixed one-line message in `packages/contracts/src/reasons.ts`, returned in the result so the model can adjust in the same conversation (for example `observation: single mention of a taste; it is saved if it comes up again in another conversation`).

## 6. Resolution and model calls

### 6.1 Entity, attribute and section

Entity lookup uses `norm_entity(x)` = `norm(x)` with `-`, `_` and `.` replaced by spaces and runs of spaces collapsed, so "memory anywhere", "Memory-Anywhere" and "memory_anywhere" match the same alias. `entity_alias.alias_norm` stores `norm_entity` values.

Resolution order (each step uses only results of earlier steps):
1. **Existing entity.** `entity` omitted or `self` → `ent_self`. Otherwise, if `norm_entity(entity)` equals an approved alias → that entity (follow `merged_into`). If neither, the entity is *new* (not created yet).
2. **Attribute**, first hit:
   1. The `attribute` hint, if it equals a registry name or alias, and its `entity_type` matches the existing entity's type (or is `any`; any type is accepted for a new entity).
   2. Deterministic patterns in `policy/attribute_patterns.yaml` on `norm(content)`, with the same type check. Initial patterns cover `city` (`^(lives|living|based|moved) (in|to) `), `employer` (`^works (at|for) `, `^employed by `), `title` (`^(is|works as) (a|an) [a-z ]{2,40} (at|for) `), `os` (`^(uses|runs|is on) (windows|macos|linux|ubuntu)`), `project.status` (`^(status|is) (idea|active|paused|shipped|archived)`), `person.relation` (`^is (my|the user's) `), and the taste verbs (`^(likes|loves|enjoys|watched|plays|reads|collects|is interested in) `).
   3. If `llm.provider` ≠ `none` and no decision row before D14 has decided: the slot proposal call (§6.2). The answer must be a registry attribute passing the same type check, or `none`.
   4. None.
3. **Create the entity** if it is new: type = the attribute's `entity_type` if that is not `self`/`any`; else `person` if the section hint resolves to People; else `project` if it resolves to Projects; else `thing`. Canonical name = `entity` as given (trimmed, ≤ 80 chars), with a `canonical` alias. `approved = 1` at T0. A new entity of type `project` from any other channel gets `approved = 0` and a review item `project_proposal`; it is stored and recalled like any entity, but it is not in the project catalog export (data-model.md §11) and has no repo link until the owner approves it.
4. **Re-check**: if the attribute's `entity_type` does not match the final entity type (and is not `any`), drop the attribute (store unslotted).
5. **Section**: memory-policy.md §9.1.

Deterministic steps 1, 2.1, 2.2, 3–5 run before the decision table; step 2.3 runs just before row D14 (§1).

### 6.2 LLM adapter

All model calls run on the server through `packages/server/src/llm/adapter.ts`. The PC never calls an LLM.

| Call | When | Sync | Timeout | Output | On timeout, error, cap reached, or `provider = none` |
| --- | --- | --- | --- | --- | --- |
| `slot_proposal` | Free-text save with no attribute from steps 1–2 | yes | 3 s | `{attribute: <registry name> \| "none"}` | Store unslotted; queue job `reslot` (retries 3 times over 24 h). A later reslot may only add a slot if the slot is empty, or mark the pair contested; it never supersedes |
| `sensitive_check` | Every save not decided by D1–D2, before D3, when `sensitive.llm_check = true` | yes | 2 s | `{sensitive_category: <id> \| null}` | Lexicon result stands |
| `judge` | Rows D14–D18 at tier ≥ T2, when `llm.judge = true` (default `false` until M2 suite P shows it helps) | yes | 2 s | `{durable: boolean}` | Skip; outcome stands |
| `extract` | Capture batches; history import | no (job) | 30 s per batch | memory-policy.md §6.12 schema | Retry 3 times with backoff 1 min, 10 min, 60 min; then status `dropped`, alert `job_failed` |
| `section_name` | Weekly section job | no | 30 s | `{name, description, aliases[]}` | TF-IDF fallback (memory-policy.md §9.2) |

- Config (`server.toml` `[llm]`): `provider` = `anthropic` | `openai` | `none` (default `none` in local mode, `anthropic` in the owner's aws deployment); `model` = a pinned, dated model id chosen in M0 (Q16), never an alias that floats; `daily_usd_cap` = 1.00; `import_usd_cap` = 20.00.
- The API key is in SSM Parameter Store at `/memory-anywhere/llm/api_key` (SecureString), delivered to the server through `/run/memory-anywhere/secrets.env` (deployment-aws.md §4). Local mode reads `MA_LLM_API_KEY` from the environment.
- Every call's cache key is `sha256(input ‖ prompt_version ‖ model_id)`, stored in `extraction_cache` (30-day TTL). A cache hit costs nothing and returns the same output, so re-runs are repeatable.
- Spend is estimated from token counts with the per-model prices in `packages/server/src/llm/prices.json` (updated with each model pin) and recorded in `llm_spend`. When the day's `live` spend reaches `daily_usd_cap`, the adapter behaves as `provider = none` until 00:00 UTC and raises alert `llm_cap`. Import spend has its own cap (§10.5).
- Bedrock is not supported in v1, because the server process holds no AWS credentials (ADR-0010).
- No-LLM mode is a supported configuration and an eval row: free text stays unslotted unless a pattern matches; capture uses §10.3's no-LLM rule; section names use TF-IDF.

## 8. Store rules

Applied when the outcome is `active` (or on promotion, or on review approval). They run inside one `BEGIN IMMEDIATE` transaction together with the commit (§11). `cur` = the current version of the memory occupying the slot. "Rights" = new tier ≤ target tier.

| Order | Condition | Action | Result reason |
| --- | --- | --- | --- |
| 0 | `supersedes` = memory X | If X is not active/contested → `NOT_FOUND` error. If caller tier ≤ X's tier: apply `change` (default `update`) to X (data-model.md §6) and write the new content as X's new version. If not: insert the new memory contested with X | `update` / `correction` / `contested` |
| 1 | `content_norm_hash` equals a current version of an active/contested memory (any entity) in scope | Add `memory_source` (and excerpt) to it | `already_stored` |
| 2 | Same `one` slot, different value, new `valid_from` known and earlier than `cur.valid_from` | Insert a closed historical memory (`change_kind = historical`, status `superseded`, `valid_to = cur.valid_from`); no contest | `historical` (reported as `active`) |
| 3 | Same `one` slot, different value, tier T3, `valid_from` unknown, `cur` tier ≤ T2 | Insert an undated historical memory (`valid_from` NULL, `valid_to = cur.valid_from`, status `superseded`); no contest | `historical` |
| 4 | Same `one` slot, different value, rights over `cur`, and not the profile-key case below | Update `cur`'s memory (`change = update` semantics) | `update` |
| 4a | Same `one` slot whose attribute has `profile_key = 1`, different value, new tier = T2, `cur` tier = T2, and `cur.client_id` ≠ the caller's client | Insert new memory; mark both `contested` (as rule 5). The profile shows the slot as `unconfirmed: <A> / <B>` until the owner resolves it | `contested` |
| 5 | Same `one` slot, different value, no rights | Insert new memory; mark both `contested`; `memory_contest` rows | `contested` |
| 6 | Same entity, same attribute (or both NULL), cosine(new, cur of candidate) ≥ `meta.dup_threshold` | Add a source. If `norm(new)` contains `norm(old)` and is longer, open a new version with the new text (`change_kind = extension`) if rights, else source only | `already_stored` |
| 7 | `many` slot, or no slot and no match | Insert a new active memory | outcome's reason |

- Rule 6 compares against the top 5 cosine candidates of the same entity, computed with the embedding of the new content (§11).
- Contested pairs: an owner resolution (admin UI) or a rule-0 save with rights resolves them; the loser becomes `superseded`, `memory_contest.resolution` is set, and an event records it.
- The `project.status` slot accepts only `idea`, `active`, `paused`, `shipped`, `archived` (after `norm()`). A save resolved to `project.status` with any other value is stored unslotted (attribute NULL) on the project entity.

### 8.1 Out-of-order and replay

Spool replays and imports may arrive after newer facts. Rules 2 and 3 handle them without false contests. A replayed `memory_save` never carries `supersedes` (the proxy refuses to spool those).

### 8.2 Rights matrix

Rule 4a is checked before rule 4. Rules 4 and 5 for a `one` slot with a different value, after rules 2 and 3 (an earlier dated `valid_from` is always historical, at any tier):

| New \ Current | T0 | T1 | T2 | T3 |
| --- | --- | --- | --- | --- |
| T0 | update | update | update | update |
| T1 | contested | update | update | update |
| T2 | contested | contested | update (contested if the slot is a profile key fact written at T2 by another client, rule 4a) | update |
| T3 | historical if undated, else contested | historical if undated, else contested | historical if undated, else contested | update |

Every supersede below T0 appears in the admin UI's Recent changes feed with one-click undo.

### 8.3 Observation promotion

When a mention is added (rows D11, D13b, D17, D19):
1. Match an open observation (memory-policy.md §8). No match → create one; outcome `observation`.
2. Count distinct sessions using `observation_mention.session_key` (§2.2). Mentions with `floored = 1` count only if at least one mention with `floored = 0` exists.
3. If the count ≥ `observation.promote_min_sessions` (2): run store rules with tier = the lowest `observation_mention.trust_tier` among counted mentions, content = the `content` of the most recent counted mention, `valid_from` = `first_seen`, `client_id` = that mention's client; all mentions become `memory_source` rows; observation status `promoted`. Outcome `active`, reason `recurred`. If the promoted memory's kind is `preference`, a review item `preference_confirm` is also created, so it can reach the profile through the one-tap confirmation like a D15 save.
4. Otherwise outcome `observation`, reason from the row.

## 9. Forget, undo, suppression, purge

### 9.1 Forget

| Caller | Allowed | Limits | Effect |
| --- | --- | --- | --- |
| Chat or coding client (`memory_forget`) | By id; only memories the client could recall (section allow-list, scope, sensitivity) | `quota_forgets_per_day` (5) | Soft forget. If the memory is T0, pinned or `sensitivity_category` set: Elicit "Forget this from all your AI apps: “<first 200 chars>”?"; Yes → forget; otherwise outcome `review` (review kind `forget_protected`), memory unchanged |
| Admin | Any id or bulk (admin UI) | none | Soft forget |

Soft forget: status `forgotten`, current version `expired_at` = now, `forgotten_at` = now, `purge_after` = now + 30 days, `suppression` row with `reason = forget`, event with undo data. Undo (admin UI) within 30 days restores the prior status, clears `expired_at` on that version and lifts the suppression.

### 9.2 Suppression matching

`hmac` = HMAC-SHA256(`meta.store_hmac_key`, norm(content)). A save matches if its `hmac` equals an unlifted suppression, or if it fills the same slot with the same normalized value (`slot_hmac`). Matching computes the HMAC under the local key and under every `foreign_suppression_key` and compares each with the suppressions of that `key_id` (data-model.md §10). The local HMAC key is part of every full export (not only `--include-auth`). Purge keeps the suppression row; it reveals nothing without the key.

### 9.3 Purge

data-model.md §9. Job `purge` runs hourly and purges memories whose `purge_after` has passed.

## 10. Capture and import extraction

### 10.1 Prompt intake

1. Coding-tool prompt hook (clients.md §3) redacts the prompt on the PC and sends `/v1/writes` entry `op: prompt` (or spools it).
2. The server accepts prompts only from class `coding` grants and only for enabled repos. It stores `session_prompt` (24 h TTL). Prompts longer than 8,000 chars are truncated.
3. If `repo.capture = 1`, the prompt joins the extraction batch for `(client_id, repo_key, tool_session)`. A batch is flushed after 10 minutes without a new prompt or at 20 prompts, as one `extract` job.
4. Extraction input is the redacted prompts only. Assistant text, tool output, transcripts, system reminders and hook output are never sent.

### 10.2 Extraction validation

For each extracted item:
1. `span` must be ≥ 8 chars and, after `norm()` on both, a substring of the prompt `prompt_id` points to. Else drop, reason `unsupported_span`.
2. Support: content words of `content` must overlap the referenced prompt's content words by ≥ 0.6 of `content`'s content words. Else drop (`unsupported_span`).
3. Items containing `[REDACTED:` are dropped.
4. The item becomes a proposal on channel `capture`, tier T2, `user_words` = span, `explicit_request` = remember intent in the prompt, `why_durable` = "extracted from the user's prompt", and runs the decision table.

After the batch completes, its prompts' `session_prompt.prompt` is kept until the 24-hour expiry (verification needs it), then deleted by job `prune`.

### 10.3 No-LLM capture

If `llm.provider = none` or the cap is reached: each prompt sentence (split on `.`, `!`, `?`, newline) that contains a remember-intent phrase becomes an observation candidate with content = that sentence (≤ 400 chars), kind `fact`, outcome forced to `observation` (reason `capture_no_llm`). Other prompts produce nothing.

### 10.4 Import rules

Importers (importers.md) produce proposals at T3. Decision rows D1–D10, D12 and D13 apply (D13 without the `qualifying_user_words` condition, since imported items carry no user words). Rows D11, D13b and D14–D19 are replaced by:

| Condition | Outcome | Reason |
| --- | --- | --- |
| Source is atomic (a list of memories) and the item passes the applicable rows | active (T3); for `kind = preference`, also a review item `preference_confirm` | `imported` |
| Source is extraction or model-written (importers.md §2) and the item passes the applicable rows and, for extraction, the span check | observation, with mention session key `import:<batch_id>:<conversation or file id>` | `imported_observation` |

For imports, rows D5 and D6 differ: a sensitive item about the user goes to review (review kind `import_sensitive`) instead of being rejected, because the owner started the import with a passkey; D3 (third party) still rejects.

So one historical conversation never creates a memory by itself; a fact mentioned in two conversations, or once in history and once live, is promoted. T3 memories never enter the profile (retrieval.md §7).

### 10.5 History extraction budget and import flow

1. **Estimate (no step-up).** `mema import <file> --dry-run` parses the export on the PC, redacts it, counts user-authored turns and characters, applies date filters (`--since`, `--until`), and calls `POST /v1/import/estimate` (scope `memory.read`) with counts only (no content). The server returns the estimate: `turns`, `input tokens ≈ chars / 4`, `output tokens ≈ 0.1 × input`, `cost_usd` from `prices.json`, minus cache hits it can identify by content hash, and the remaining `import_usd_cap` budget.
2. **Commit (one step-up).** `mema import <file> --commit` requests step-up for command `import` with args `{source_type, file_sha256, item_count, estimate_usd}`. The approval page shows these values rendered by the server. The owner types the estimate rounded up to whole dollars to confirm, then approves with a passkey. The server creates the `import_batch` and binds the step-up token to that batch id: the token is multi-use, valid for 60 minutes, and only for `POST /v1/admin/import` calls with that `batch_id`.
3. **Upload.** The client sends items in batches of ≤ 100 items and ≤ 1 MiB per request. Each item carries its idempotency key (§2.3), so a repeated batch is a no-op.
4. **Resume.** If the token expires or the connection drops, `mema import <file> --commit --resume <batch_id>` requests a new step-up for the same batch (same file hash, same estimate) and continues; items already recorded in `import_item` are skipped by their keys.
5. **Cap.** `import_usd_cap` (20.00) is a hard stop across all batches: when cumulative import spend reaches it, the batch status becomes `aborted_budget`; items already processed stay. Re-running continues from the cache and the idempotency keys. Atomic sources make no LLM calls and cost nothing.
6. Only user-authored turns are extracted (importers.md §3).

## 11. Transaction and commit

For an `active` outcome, in order, inside `BEGIN IMMEDIATE` (retry on `SQLITE_BUSY` up to 5 times with 50 ms backoff):
1. Compute the embedding of `doc_prefix + content` before opening the transaction (it is CPU work; the transaction must stay short).
2. Store rules (§8).
3. Insert/update `memory`, `memory_version`, `source`, `memory_source`.
4. Update `memory_fts` for affected current versions (delete old row, insert new).
5. Insert `embedding`.
6. Insert `event` rows (hash-chained, data-model.md §2).
7. Insert `write_request` with the exact result.
8. Commit. Then, outside the transaction: invalidate the profile and repo-context caches for affected entities (retrieval.md §8), and update `client_policy.last_policy_version`.

Observation and review outcomes use the same transaction shape with their own tables.

## 12. Thresholds

The calibrated thresholds are listed below. Every other number in this spec is a named constant in `packages/server/src/config/defaults.ts`, exposed in `server.toml`, and changed only with a policy version.

| Threshold | Initial | Stored in | Calibrated in | By |
| --- | --- | --- | --- | --- |
| `dup_threshold` (cosine, rule 6, observation match) | 0.92 | `meta` | M1 | suite W dev duplicate pairs: lowest value with duplicate precision ≥ 0.98 |
| `abstain_cosine` (recall abstention) | 0.30 | `meta` | M1 | LongMemEval-S dev subset (abstention questions and the rest): maximize abstention F1 with non-abstention R@5 loss ≤ 1 point |
| `sections_cluster_threshold` | 0.60 | `meta` | After M3, on the owner's real Unsorted memories (fixed at 0.60 until then; synthetic clusters teach little) | pairwise F1 against 50 owner-labelled pairs, inside the owner's 50-item spot-check budget only if items remain; else kept at 0.60 |
| `support_min` (qualifying user words) | 0.5 | `server.toml` | M2 | suite P dev: max stored precision with stored recall ≥ 0.8 |
| `capture_support_min` | 0.6 | `server.toml` | M3 | suite W capture items: drop rate of correct items ≤ 5% |

All are per embedding model where they depend on vectors. Changing the model triggers recalibration (data-model.md §8). Model-reported confidence is never used.

## 13. Dry run

`/v1/writes` and `mema import` accept `dry_run: true`. The pipeline runs through step 7 inside a transaction that is rolled back, and returns `{inserted[], sourced[], updated[], contested[], observations[], reviews[], rejected[]}` with ids and reason codes (no content in logs; content only in the CLI's own output).

## 14. Required tests

- One table-driven unit test per decision row (D1–D19, including D10a and D13b) and per store rule (0–7, including 4a), each with a passing and a non-passing case, in `packages/server/test/decision-table.test.ts` and `store-rules.test.ts`.
- Property tests (fast-check, ≥ 1,000 runs each): replaying any sequence of write requests twice gives the same content hash (data-model.md §12); any interleaving of saves for one `one` slot leaves exactly one current active memory or one contested pair; forget then undo restores the identical content hash; purge leaves no plaintext (S-PURGE).
- Fault injection: kill the server during a spool drain at random points (100 runs); afterwards the store has no duplicate sources and every spool entry has exactly one `write_request`.
